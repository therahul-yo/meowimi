# Design

The hard part is not issuing a search query: it is knowing *what to search for*. Search Chat stores each user and assistant message with an absolute timestamp in local SQLite. On every turn it supplies the transcript, timestamped in the browser's time zone, to a reasoning model with one tool, OpenAI's hosted web search. The model can resolve “last Tuesday,” find the earlier shortlist and baseline claims, then search current primary sources for each item. It is instructed to distinguish verified changes from current facts, missing baselines, and inconclusive searches. It should ask for missing context rather than invent it. The UI streams text and shows clickable source links; a failed or interrupted turn is not written as a completed exchange.

A single model call handles both ordinary conversation and research. This avoids an extra classifier on the critical path and lets the model decide whether to search and refine queries as evidence arrives. A low reasoning effort reduces latency, while hosted search handles retrieval and citations. The complete transcript preserves exact wording and old assistant answers rather than relying on a lossy summary. Server-side keys, parameterized SQL, sanitized Markdown, localhost binding, a single-flight guard and transactional writes keep the local prototype straightforward. The browser's time zone is validated; stored timestamps remain UTC.

I rejected a vector-only memory store: semantic retrieval can miss an exact date, an obscure item in a shortlist, or the answer being checked. I also rejected hard-coded keyword routing and a fixed search for each product: both can fail on indirect references or waste searches on simple conversation. The current design has a deliberate ceiling: it rejects a very long history rather than silently dropping older context. It is a single-user local app, not an authenticated hosted service. Search coverage, temporal interpretation and claim-level correctness depend on the model and available sources; a source link is not proof of every claim. Costs and latency vary with model and searches.

With another week I would build a dated, conversation-level evaluation set with known baselines, changed and unchanged prices, missing history, conflicting sources, time-zone boundaries and prompt-injection pages. I would measure answer accuracy, citation support, recall, latency and cost, then add hybrid date/lexical/semantic retrieval with neighboring turns and coverage checks for long histories. I'd add claim-to-source citation validation, explicit search progress, cancellation, user-controlled history export/deletion, and authenticated per-user isolation before deployment. I would compare model and retrieval configurations on that evaluation rather than assuming a more elaborate pipeline is better.
